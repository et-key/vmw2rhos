# vmw2rhos 移行ツール設計

作成日: 2026-10-09  
状態: 初期設計。実装および製品バージョンごとの対応確認は未実施。

## 1. 目的と設計方針

vSphere上の複数のゲストOSを、関連するストレージ、ネットワーク、配置ルールとともにRed Hat OpenShift Virtualizationへ移行する。構成の収集、移行計画、事前処理、移行、検証を一つの操作の流れにまとめ、手作業と作業者の拘束時間を減らす。

最優先は使いやすさと移行の確実性であり、転送速度ではない。時間のかかる処理はバックグラウンドで継続し、利用者が画面を閉じても実行状態を失わない。処理時間とサービス停止時間は別に管理する。

基本操作は「構成を収集 → 表を確認・編集 → 事前チェック → 開始 → 結果を確認」とする。通常は共通の推奨設定を使い、例外だけ個別に編集する。判断できない構成を推測で実行せず、理由と必要な対応を表に示す。

本設計の主対象はゲストOSを維持するVM移行である。アプリケーションのコンテナ化は対象外とする。OS更新は移行に付随する処理として扱うが、すべてのOS・更新経路を自動対応することは保証しない。

## 2. 利用者の操作

1. vCenterおよび移行先OpenShiftへの接続を登録する。
2. VM、ディスク、ネットワーク、タグ、フォルダー、Affinity設定などを収集する。
3. 移行対象を選び、Namespace・ネットワーク・ストレージの共通対応ルールを設定する。
4. VM一覧から要対応の行を確認し、必要な個別設定を編集する。
5. 事前チェックの結果を確認し、問題を修正する。
6. 移行開始とサービス切替の時間帯を指定して実行する。
7. 起動・通信・データ・アプリケーションの検証結果を確認する。

初期画面ではVM名、OS、移行先Namespace、Warm/Cold、判定、進捗を中心に表示する。ディスク、NIC、配置ルール、例外処理は行を開いて編集する。検索、絞り込み、複数行への一括適用を提供する。

所要時間の見積りは推定であることを示す。時間が算出できない場合は無理に数値を出さず、現在の工程、転送量、待機理由、最終更新時刻を表示する。

## 3. 移行表と対応ルール

### 3.1 VM一覧

| 項目 | 内容 |
| --- | --- |
| 移行元 | 接続先、VMの安定した識別子、名前、フォルダー、タグ |
| ゲストOS | 種類、バージョン、取得元、取得日時、確認状態 |
| リソース | CPU、メモリ、起動方式、仮想デバイス |
| 移行先 | クラスタ、Namespace、VM名、ラベル、リソース設定 |
| 関連構成 | ディスク、NIC、配置ルール、依存VMへの参照 |
| 移行計画 | Warm/Cold、グループ、順序、開始時間、切替時間帯 |
| 例外処理 | OS更新、ドライバー変更、事前・事後処理への参照 |
| 判定 | 対応可能、要設定、要手動対応、未確認、実行不可とその理由 |
| 実行状況 | 現在工程、進捗、待機理由、エラー、検証結果 |

収集した元の設定と適用予定の設定を並べて表示する。未取得、明示的な空値、変更なし、変更指定を区別する。機密情報は表やエクスポートに含めない。

### 3.2 共通ルールと個別変更

Namespaceはフォルダー・タグ・移行グループなどから割り当てられる。ネットワークはポートグループ、ストレージはデータストアや領域の用途などから対応を設定する。

設定の優先順位は「VM・ディスク・NIC単位の明示指定 → 条件に一致する共通ルール → 既定値」とする。同順位のルールが複数一致する場合は競合として表示し、解消するまで実行しない。各値には採用したルールと変更者を記録する。

表の保存形式として、バージョン付きの構造化データを正本とする。CSVは編集・交換用として利用できるようにし、関連表は安定したIDで結び付ける。インポート時は型、参照、重複、競合を検証し、変更差分を表示する。具体的な正本形式は実装時に決定する。

## 4. ストレージ設計

### 4.1 管理単位

ストレージはサーバー名やVM単位だけでなく、「ディスク・データ領域」と「接続関係」で管理する。複数のVMが同じ領域を使う場合、共有領域を一つの対象として登録し、各VMから参照する。誤ってVMごとに独立したコピーを作らない。

バックエンドの物理構成が見えない場合も、把握できた論理的な接続と用途を記録する。vSphereの情報だけでは把握できないゲスト内マウントや外部接続は、任意のゲスト調査または手動入力で補い、未確認のまま完了扱いにしない。

### 4.2 領域・接続の編集表

| 項目 | 内容 |
| --- | --- |
| 識別 | 領域ID、移行元ID、所有者、接続するVM |
| 用途 | OS、データ、ログ、共有領域など |
| 接続 | 仮想ディスク、ゲストからの外部接続、共有接続など |
| 構成 | 容量、使用量、パーティション、ファイルシステム、マウント先、確認状態 |
| 要件 | 性能、アクセス形態、同時書込み、整合性、暗号化に関する要件 |
| 移行方法 | コピー、継続利用、再接続、事前作成領域への移行、要手動対応 |
| 移行先 | Namespace、StorageClass、PVCまたは外部接続先、割当容量 |
| 切替 | 同期方法、書込み停止、関連VMの停止順序、再接続順序 |
| 検証 | 容量、接続、マウント、権限、データ・アプリケーション整合性 |

StorageClassの名称一致だけでは適合とみなさない。容量、アクセス要件、ボリュームの利用形態、配置制約、性能要件が満たされるかを確認する。実容量や性能の確認ができない場合は不足情報として示す。

### 4.3 想定する構成パターン

| パターン | 計画で扱う内容 |
| --- | --- |
| OSとデータが同一ディスク | パーティション構成を維持する方針と検証 |
| OS・データが別ディスク | 領域ごとの対応、接続順序、識別子の変化 |
| 複数VMが共有する領域 | 共通領域の識別、関連VMをまとめた切替、同時アクセス要件 |
| ゲストからNFS・SMB・iSCSI等へ接続 | 接続継続または変更、経路、認証、マウントの確認 |
| RDM・特殊デバイス等 | 対応確認、変換経路、事前処理または手動対応の表示 |
| ストレージサーバー自体がVM | 利用VMとの依存、サービスの起動順序、データ保全 |
| 一つに見えるストレージの内部に複数領域 | 論理領域と利用VMの対応を保持し、領域ごとに計画 |

これは調査・判定すべきパターンの一覧であり、全パターンの自動移行を保証する対応表ではない。

### 4.4 データ整合性

データ転送の完了とアプリケーション整合性の確認は別工程にする。必要に応じてサービス停止、書込み停止、最終同期、マウント・権限確認、アプリケーション固有の検証を計画する。チェックサム等は対象と費用に応じて選択し、検証範囲を記録する。

共有領域や依存VMのグループでは、グループ全体の切替条件を満たすまで移行先への書込みを開始しない。移行元と移行先の二重起動・二重書込みを防止する。

## 5. ネットワークとNamespace

### 5.1 NICとネットワークの対応

NICごとにポートグループ、取得可能なVLAN設定、MAC、接続状態を収集する。ゲストIP、DNS、経路は取得元と確認状態を付け、ゲスト調査が必要な情報を区別する。

共通対応表では移行元ネットワークに対する移行先接続を設定し、NIC単位の上書きを許可する。移行先ネットワーク定義、VLAN、MACの保持方針、IP・DNS・経路の維持または変更を編集できるようにする。

VLAN番号の一致だけで接続可能とは判断しない。移行先のノード、物理ネットワーク、ネットワーク定義、アドレス重複、到達性を確認する。トランク等の構成は単一VLANとして扱わず、取得した構成と実装可能な対応を明示する。

### 5.2 Namespaceへの配置

VM名の競合、Namespaceの存在・作成可否、権限、Quota、ラベル、必要なネットワーク・ストレージ関連リソースを検証する。関連リソースのスコープと利用条件に従って配置し、Namespaceが異なる共有領域を単純に一つのPVCで参照できるとは仮定しない。

NamespaceやVM名を変更した場合は、関連参照を再計算し、表で変更内容を確認できるようにする。

## 6. Affinity・依存関係

VM同士、およびVMとホストのAffinity／Anti-Affinityを収集し、対象、条件、必須・推奨の強度、有効状態を表にする。元の設定は保存し、移行先の配置方針への変換結果を別列で示す。

vSphereホストとOpenShiftノードを同一視しない。移行先のノードラベルやグループなどへの対応を定義する。意味を維持できないルールは要対応として表示し、無断で破棄・弱体化しない。個別変更は可能とし、変更理由を記録する。

配置ルールとサービスの起動依存は別に管理する。依存関係はストレージ共有・外部接続などから収集可能な情報を補助表示し、利用者が編集する。循環依存は検出し、グループ化や明示的な切替手順で解消する。

## 7. Warm／Coldと例外処理

Warm／ColdはVM単位またはグループ単位で選択する。Warmは事前転送と切替時の最終同期、Coldは停止後の移行として工程を表示する。実際の方式・利用条件は採用する移行基盤の仕様に従う。Warmが選択不能な場合は理由を示し、Coldへ無断で変更しない。

OS更新、ドライバー変更、事前・事後スクリプトなどは例外処理表として編集する。

| 項目 | 内容 |
| --- | --- |
| 対象と条件 | VM・グループ、OS・バージョン、実行条件 |
| 処理 | 定義済み処理の種類、必要な引数、独自スクリプトへの参照 |
| 実行位置 | 移行元・移行先・管理環境、事前・切替前・事後 |
| 前提 | バックアップ、空き容量、認証、パッケージ、再起動の要否 |
| 判定 | 成功条件、タイムアウト、検証方法 |
| 失敗時 | 停止、再試行条件、手動対応、復旧手順 |

自由記述の指示をそのまま自動実行しない。処理は型付きの設定と実行定義にする。OSの更新経路・ライセンス・サポート条件は個別に確認し、移行元で更新するか移行先で更新するかを明示する。更新不能な場合は代替計画または手動対応として表示する。

不可逆な更新は自動切り戻し可能と表示しない。再実行して安全な処理かを定義し、安全性が不明なスクリプトは自動再試行しない。

## 8. 自動実行と状態管理

### 8.1 計画の確定

実行前に収集情報、対応ルール、例外処理から実行計画を作成し、差分とチェック結果を提示する。実行は特定の計画版に固定する。実行中の表編集は次の計画版に保存し、進行中の処理へ直接反映しない。

構成が収集後に変わった場合は再確認する。特にディスク、接続先、容量、電源状態などの変化は影響を判定し、計画の再作成または停止が必要か示す。

### 8.2 工程

「下書き → 事前チェック → 実行可能 → 事前処理 → 転送 → 切替待ち → 切替 → 検証 → 完了」を基本とする。別状態として失敗、手動対応待ち、停止要求、取消、切り戻し中、切り戻し完了を持つ。

各工程には開始・終了時刻、入力した計画版、実行結果、再開地点を記録する。全VMの成功だけでなく、必要な共有領域・ネットワーク・例外処理・検証が成功してからグループを完了にする。

### 8.3 継続・再開

実行状態はサーバー側に永続化する。ブラウザーの閉鎖や管理プロセスの再起動で状態を失わない。再開時は外部の実状態を照合し、完了した処理を重複実行しない。

依存する工程は順序を守り、独立した転送は容量・帯域・負荷を見ながら並行実行できるようにする。同時実行数は保守的な既定値と変更オプションを設ける。

停止・取消は工程ごとに可能な意味を示す。転送停止とサービス切替の中止は区別し、危険な中間状態を残す場合は復旧に必要な操作を表示する。

## 9. 事前チェック・検証・切り戻し

事前チェックは、接続・権限、製品バージョンとOSの対応、容量、ストレージ要件、ネットワーク対応、Namespace、配置制約、依存関係、例外処理、切替時間帯を対象とする。

結果は「実行を妨げる問題」「確認が必要な事項」「参考情報」に分け、対象行、理由、対処方法を表示する。必須情報の未確認を成功扱いにしない。共通問題はまとめて表示し、修正後は影響範囲を再チェックする。

移行後はVMの起動だけでなく、OS、ディスク接続、マウント、権限、NIC、IP・DNS・経路、必要な通信、配置ルール、アプリケーションの検証を行う。自動確認と利用者による確認を区別し、証跡を残す。

切り戻しは、移行先で書込みが始まる前後で条件を分ける。書込み後は移行元を再起動するだけではデータを戻せないため、逆同期・バックアップ復元・手動復旧などの必要な手順を計画する。移行元の自動削除は初期設計に含めず、検証後の保持・廃止方針は別操作として扱う。

## 10. 論理構成とデータモデル

| 構成要素 | 責務 |
| --- | --- |
| 収集アダプター | vSphere、OpenShift、任意のゲスト調査から構成を収集 |
| 構成・計画ストア | 収集時点、編集表、版、接続関係、計画、実行状態を保存 |
| 計画・判定エンジン | 対応ルール適用、対応可否、依存解決、事前チェック |
| 実行エンジン | 工程制御、再開、並行実行、外部処理との状態照合 |
| 移行アダプター | 採用する移行基盤への要求と状態取得 |
| 例外処理・検証アダプター | OS更新などの定義済み処理と検証を実行 |
| UI・入出力 | 表編集、差分、進捗、CSV等の交換、結果出力 |

主要データはConnection、DiscoverySnapshot、VM、Volume、VolumeAttachment、NIC、NetworkMapping、NamespaceMapping、PlacementRule、Dependency、ExceptionAction、MigrationGroup、PlanRevision、Run、StepResultとする。

収集情報と利用者の変更を分離し、再収集しても個別指定を失わない。削除・置換された対象への参照は無効として検出する。接続先と移行元の安定したIDを組み合わせ、名前変更による取り違えを防ぐ。

既存の移行基盤をアダプター経由で利用する方針とし、Migration Toolkit for Virtualization等を候補にする。採用製品、API、対応バージョン、追加ネットワークやストレージを扱える範囲は実装前に確認する。

## 11. 認証・変更記録

収集、計画編集、実行を権限として分離する。接続情報は機密情報への参照として保持し、表・CSV・ログに認証情報を出力しない。ゲスト操作や独自スクリプトの実行は必要な対象と権限に限定する。

誰が、いつ、どの計画を変更・実行したかを記録する。操作、外部応答、エラーはVM・グループ・工程に結び付け、診断に必要な情報を残す。

## 12. 初期実装の受入条件

- 複数OSのVMを一覧化し、未対応・未確認を理由付きで区別できる。
- Namespace、Warm/Cold、ディスク、NIC、配置ルール、例外処理を共通ルールと個別指定で編集できる。
- 外部・共有ストレージを関連VMと結び付け、必要な手動対応も計画に残せる。
- 未解決の必須設定や競合がある計画を実行可能としない。
- 計画差分を確認し、複数VMを依存順序に従って一括実行できる。
- 画面を閉じても処理が継続し、管理プロセス再起動後に状態照合して再開できる。
- 二重作成・二重書込みを防止し、失敗した対象と次の操作が分かる。
- 起動、ストレージ、通信、必要なアプリケーション検証を経て完了を判定する。
- 実行時間と停止時間を別に示し、切替時間帯を設定できる。
- 移行元の自動削除を行わず、切り戻しの可能範囲と条件を示す。

確認シナリオには、OS混在、複数NICとVLAN変更、Namespace変更、独立データディスク、共有領域、外部ストレージ、Affinity変換不能、OS更新失敗、転送中断、管理プロセス再起動、容量不足、切替後の検証失敗を含める。

## 13. 実装前の確認事項

- 対象となるvSphere、OpenShift、移行基盤のバージョンと組合せ。
- OSごとの対応、変換要件、更新経路、ゲスト調査の方法。
- Warm/Coldの適用条件と、外部・共有領域との整合性確保。
- VLAN、複数NIC、MAC、IP変更、Affinity変換の実装範囲。
- StorageClass、領域の利用形態、共有方式、バックアップ・復旧手段。
- UIと実行基盤の配置、計画保存形式、認証・権限管理。

初期段階では収集・表編集・判定・計画出力を固め、次に標準構成の移行実行、最後に例外処理と追加パターンへ広げる。汎用性は未対応を隠すことで実現せず、構成を表現でき、対応を追加できる設計で確保する。
